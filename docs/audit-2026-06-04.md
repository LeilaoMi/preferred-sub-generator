## 1. 总体评价

这个项目定位清晰：**用户已经有一个 VLESS 节点，本项目只替换入口地址为测速较好的 Cloudflare Edge IP，并输出多客户端订阅格式**。相比公开订阅聚合器，这种“模板私有 + Edge 优选”的方向更干净，也更容易控制风险。

项目当前优点：

1. 代码结构清楚，Pages Functions 与业务模块分离。
2. 测试覆盖很不错，已有 56 个 Node test。
3. 已明确不混入 ProxyIP / SOCKS / NAT64 / 公益节点，边界清楚。
4. 真实模板不放 GitHub Secrets，而是保存在 Cloudflare KV，思路正确。
5. `/api/template` GET 已收窄为安全预览，不返回原始 VLESS，这是重要修复。
6. GitHub Actions 会先跑 test / preflight / source validation，再更新 KV。
7. 多客户端输出格式已覆盖 vless / v2rayNG / Clash / Sing-box / Shadowrocket。

但它现在最大的短板也很明确：**“私用”主要靠不要公开域名这条约定，而不是技术强制**。因为 `/sub` 和 `/best` 默认公开，任何拿到域名的人都可以直接拉取基于真实 TEMPLATE 生成的完整订阅。对“真实节点参数绝不能外泄”的目标来说，这是第一优先级。

# P0 · 隐私 / 架构底线

## P0-1. `/sub` 公开等价于公开真实 VLESS 节点参数

**位置**：`file src/api/sub.js`

现状：

```js
const template = await readTemplate(env.SUB_KV, templateKeyFromUrl(url));
...
return cachedTextResponse(generateVlessSubscription(template, nodes));
```

`/sub` 默认无需 token。只要别人知道你的域名，就能请求：

```text
/sub?type=vless
/sub?type=v2rayng
/sub?type=clash
/sub?type=singbox
```

这些输出里会包含：

- UUID
- Host
- SNI
- path
- TLS/WS 参数
- 由模板派生出的完整 VLESS 节点

**风险**：项目 README 虽然写“请不要公开部署域名”，但技术上域名一旦被分享、日志泄露、浏览器历史同步、客户端订阅地址外传，就等于真实节点参数外泄。

**建议**：增加订阅读取保护，至少支持三种模式：

```text
SUB_PUBLIC=1              # 兼容旧行为，公开订阅
SUB_READ_TOKEN=xxx        # /sub /best 需要 Bearer 或 ?t=
SUB_SECRET_PATH=随机路径  # /s/<secret>/sub 才能访问
```

默认建议改为：

```text
SUB_PUBLIC=0
```

短期兼容可以先文档提示，但代码层最好给开关。

## P0-2. `/sub` 使用 `Cache-Control: public` 缓存含真实节点的订阅

**位置**：`file src/utils/response.js`

现状：

```js
"Cache-Control": "public, max-age=600",
```

所有 `cachedTextResponse()` 都会 public cache。订阅内容包含完整 VLESS 参数，属于敏感私有数据，不适合公共缓存。

**风险**：

- CDN / 中间层可能缓存完整订阅；
- token 化以后如果仍 public cache，可能把 A 用户带 token 的响应缓存给其他人；
- 订阅改了模板后，旧参数 10 分钟内仍可能被返回。

**建议**：

订阅类响应改为：

```text
Cache-Control: private, no-store
```

如果坚持缓存，至少：

```text
Cache-Control: private, max-age=300
Vary: Authorization
```

`/best` 只返回 Edge IP 时可以 public cache，但 `/sub` 不应 public。

---

## P0-3. 管理接口仍支持 `?token=`，有泄露风险

**位置**：`file src/security/auth.js`、README API 说明

现状：

```js
const queryToken = url.searchParams.get("token") || "";
...
} else if (queryToken) {
  candidate = queryToken.trim();
}
```

README 也写了：

```text
/api/template?token=你的SUB_TOKEN
```

**风险**：query token 容易进入：

- 浏览器历史；
- Cloudflare / Pages 请求日志；
- 第三方 Referer；
- 截图、复制链接、收藏夹；
- 客户端调试日志。

**建议**：

1. 默认只接受：

```text
Authorization: Bearer <SUB_TOKEN>
```

2. 如果为了临时兼容 query token，加环境变量：

```text
ALLOW_QUERY_TOKEN=1
```

3. README 删除 query token 示例。

---

## P0-4. 首页和 admin 页面支持 URL token 自动填充

**位置**：`file public/index.html`、`file public/admin.html`、`file public/admin/index.html`

现状搜索结果显示：

```js
new URL(location.href).searchParams.get("token")
location.hash.replace(/^#token=/, "")
```

**风险**：hash 比 query 安全一点，不会发到服务器，但 query token 会进入请求 URL、历史和可能的日志。

**建议**：

- 删除 `?token=` 自动填充；
- 只保留 `#token=`，并在读取后立即：

```js
history.replaceState(null, "", location.pathname);
```

- 或者完全取消 URL token，只允许手动粘贴。

---

## P0-5. “私用”没有强制 Cloudflare Access / IP 白名单 / 订阅 token

**位置**：整体架构

现状：管理接口有 `SUB_ALLOWED_IPS`，但订阅接口没有类似控制。

**风险**：真实节点不是只存在 KV，它会通过 `/sub` 按需派生为完整订阅。

**建议**：至少提供一种硬保护：

- Cloudflare Access 保护整个 Pages 域名；
- `/sub` 需要只读 token；
- `/sub` 只允许固定 UA 或 IP 白名单；
- 管理域名与订阅域名拆开，订阅域名使用随机路径。

我的建议是：**默认 SUB_READ_TOKEN，公开模式必须显式打开**。

---

## P0-6. `/best` 公开暴露优选 Edge 池，可被他人复用和爬取

**位置**：`file src/api/best.js`

现状：`/best` 公开返回当前或历史 `BEST_IPS`。

**风险**：虽然不含 UUID，但会暴露你的优选结果、检测规律、COLO、延迟，别人可直接复用你的 Edge 池并加重访问压力。

**建议**：

- `/best` 与 `/sub` 使用相同只读 token；
- 或返回脱敏版本：只给数量、更新时间，不给全部 IP；
- 首页只显示前 3 个示例，不公开完整 best JSON。

# P1 · 安全硬化

## P1-1. API 响应缺统一安全 headers

**位置**：`file src/utils/response.js`

当前只设置 Content-Type、Cache-Control、ETag。建议统一加：

```text
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Robots-Tag: noindex,nofollow,noarchive
Permissions-Policy: camera=(), microphone=(), geolocation=()
Content-Security-Policy: default-src 'none'; frame-ancestors 'none'
```

对 HTML 页面单独设置更宽 CSP。

---

## P1-2. public 页面使用 `innerHTML`，需要统一转义策略

**位置**：`file public/index.html`、`file public/admin.html`

搜索结果显示多处：

```js
subscriptionList.innerHTML = ...
resultHint.innerHTML = ...
previewBox.innerHTML = ...
```

如果插入内容来自用户输入的 VLESS remark/name，可能 XSS。

**建议**：

- 对节点名称、错误信息、preview 字段统一 `escapeHtml()`；
- 或改用 `textContent` / DOM API 创建节点；
- 增加 XSS 回归测试：模板 name 为 `<img onerror=alert(1)>` 时页面不执行。

---

## P1-3. `rate-limit` Map 没有容量清理

**位置**：`file src/security/rate-limit.js`

现状：

```js
const buckets = new Map();
```

没有过期清理和最大容量。虽然 Cloudflare isolate 会重启，但大量不同 IP 请求管理接口时仍会增长。

**建议**：

- 每 N 次请求清理过期 bucket；
- 设置最大 bucket 数，例如 5000；
- 超过后删除最旧项。

---

## P1-4. IP 白名单读取 `x-forwarded-for` 时没有取第一个 IP

**位置**：`file src/security/auth.js`

现状：

```js
request.headers.get("x-forwarded-for") || "unknown"
```

如果 header 是 `a, b, c`，会和白名单精确匹配失败。Cloudflare 下优先 `cf-connecting-ip`，但 fallback 仍建议规范化。

**建议**：

```js
const xff = request.headers.get("x-forwarded-for") || "";
return request.headers.get("cf-connecting-ip") || xff.split(",")[0].trim() || "unknown";
```

---

## P1-5. token 轮换只有 `SUB_TOKEN_NEXT`，缺少审计/过期提示

**位置**：`file src/security/auth.js`、文档

当前支持双 token，但不知道 NEXT 什么时候生效、什么时候删除旧 token。

**建议**：

- README 增加轮换流程：添加 NEXT → 客户端切换 → 删除旧 token；
- `/status` 不暴露 token，但可暴露 `tokenRotationEnabled: true`；
- 模板保存审计中记录使用 primary/next，但不要记录 token 值。

---

## P1-6. `/health` 暴露 `templateExists`

**位置**：`file src/api/health.js`

现状：

```js
{ ok, kv: true, templateExists, bestIpsCount }
```

**风险**：攻击者可判断该部署是否已配置真实模板。

**建议**：公开 `/health` 最小化：

```json
{ "ok": true }
```

详细信息放 `/health/full` 并鉴权。

---

## P1-7. TEMPLATE_AUDIT 记录 IP 与 UA，需要明确保留周期

**位置**：`file src/api/template.js`

当前记录：

```js
lastTemplateUpdateIp
lastTemplateUpdateUserAgent
```

这对审计有用，但属于访问者数据。

**建议**：

- 文档说明会保存最近一次管理 IP/UA；
- 只保留最近一次是可以的；
- 可加 `DISABLE_TEMPLATE_AUDIT=1` 或只保存 IP hash。

---

## P1-8. 缺少 robots/noindex 策略

**位置**：Pages Functions 和 public

建议新增：

- `file public/robots.txt`：`Disallow: /`
- API 统一 `X-Robots-Tag`；
- README 明确不要让搜索引擎索引。

---

## P1-9. 管理接口错误原因过于具体

**位置**：`file src/security/auth.js` / `file src/api/template.js`

`Missing SUB_TOKEN` 返回 500 是合理运维提示，但公开接口直接告诉攻击者配置状态。

**建议**：对外统一：

```json
{ "error": "Unauthorized" }
```

内部可通过日志/health full 查看缺配置。

# P2 · 可靠性 / 数据质量

## P2-1. `BEST_IPS_时间戳` 版本快照没有清理策略

**位置**：`file scripts/update-kv.js`

每次运行写：

```js
BEST_IPS_YYYYMMDDTHHMMSSZ
```

Cron 每 6 小时，一年约 1460 个 key。KV key 多了以后维护困难。

**建议**：

- 只保留最近 7/14/30 个版本；
- 写 `BEST_IPS_VERSION_INDEX`；
- 每次更新后删除超出保留数量的旧 key。

---

## P2-2. 本次可用节点低于 20 就回退，但没有“连续失败”状态

**位置**：`file scripts/update-kv.js`

当前：

```js
protectedByPrevious = nextBestIps.length < MIN_AVAILABLE_TO_OVERWRITE && previousBestIps.length > 0
```

这是好保护，但如果连续 10 次都回退，系统仍可能看起来“available 很多”。

**建议**：STATUS 增加：

```json
consecutiveFallbacks
lastSuccessfulRefreshAt
lastRawAvailable
```

超过阈值时 `/status` 显示 degraded。

---

## P2-3. Edge 检测 fallback 到 TCP 可能混入非 Cloudflare Edge

**位置**：`file scripts/lib/check.js`

现状：HTTP/TLS 检测失败后：

```js
const latency = await checkTcp(...)
return { latency, colo: "", edgeVerified: false }
```

这会保留 TCP 可达但没有 `cf-ray` 的节点。对“Cloudflare Edge 优选”目标来说，应该可配置是否允许。

**建议**：

```text
REQUIRE_CF_RAY=1   # 默认只保留 edgeVerified=true
ALLOW_TCP_ONLY=1   # 兼容模式
```

---

## P2-4. Cloudflare 官方 CIDR 每段只抽样 4 个，覆盖偏弱

**位置**：`file sources/edge/remote.json`、`file scripts/lib/candidates.js`

官方 CIDR 很大，每段 4 个点可能不足以覆盖真实可用边缘。

**建议**：

- 改为按 /24 或边界/中点/随机混合抽样；
- 引入固定 seed，保证结果可复现；
- 每次只抽一部分，滚动覆盖。

---

## P2-5. IPv6 候选源有解析，但检测/客户端路径需单独加强

项目支持 IPv6 地址解析和 VLESS 方括号测试，但 GitHub Actions 的网络环境、客户端格式、Cloudflare Edge 可用性都需要独立统计。

**建议**：STATUS 增加：

```json
ipv4Available
ipv6Available
```

并允许 `/sub?family=v4|v6|all`。

---

## P2-6. 远程源抓取没有单源大小限制

**位置**：`file scripts/lib/candidates.js`

`collectCandidates` 直接 `response.text()`。若远程源异常返回超大内容，会吃内存。

**建议**：使用 stream 读取并设置最大字节数，例如 5MB。

---

## P2-7. 远程源失败没有 source health 报告

现在 STATUS 有 sourceCount，但缺少每源成功/失败/候选数。

**建议**：写入：

```json
SOURCE_HEALTH
```

包含每个 source 的 HTTP 状态、候选数、错误、耗时。

---

## P2-8. 平均延迟可能被旧 fallback 数据误导

`averageLatency(bestIps)` 如果使用 previousBestIps，则展示的是旧节点平均延迟，不是本次检测。

**建议**：STATUS 区分：

```json
averageLatencyCurrentBest
averageLatencyNewScan
protectedByPrevious
```

---

## P2-9. `readTemplate` 支持 JSON 模板，但写入只允许 vless://，文档应明确

**位置**：`file src/api/kv.js`、`file src/api/template.js`

读取兼容 JSON，但 POST 只允许 `vless://`。这是合理的向后兼容，但文档应说明 JSON 是旧格式兼容，不推荐手写。

# P3 · CI/CD 与运维

## P3-1. GitHub Actions 未声明最小权限

**位置**：`file .github/workflows/update.yml`

建议添加：

```yaml
permissions:
  contents: read
```

该 workflow 只读仓库并写 Cloudflare KV，不需要 contents write。

---

## P3-2. Actions 没有 concurrency 控制

建议添加：

```yaml
concurrency:
  group: preferred-sub-generator-update
  cancel-in-progress: false
```

避免手动触发和 cron 并发写 KV。

---

## P3-3. Actions 没有 timeout-minutes

建议添加：

```yaml
timeout-minutes: 20
```

避免远程源/网络异常导致 runner 卡太久。

---

## P3-4. 更新完成没有生成 GitHub step summary

建议 `file update-kv.js` 输出结构化摘要，并由 workflow 写入 `$GITHUB_STEP_SUMMARY`：

```text
available / newAvailable / fallbackActive / averageLatency / sourceCount
```

---

## P3-5. 没有线上 smoke check

CI 只写 KV，不验证 Pages 线上是否能读到新数据。

建议增加可选 smoke：

```bash
curl -fsS https://你的域名/status
curl -fsS https://你的域名/best?n=1
```

域名通过 secret/variable 配置。

---

## P3-6. Cloudflare KV namespace id 写在 wrangler.toml，易 fork 后误用

**位置**：`file wrangler.toml`

当前 id 是具体值。对于开源仓库，建议 README 强提醒 fork 必改，或提供 `file wrangler.example.toml`。

---

## P3-7. 缺少 wrangler deploy 验证命令

README 有 Pages 部署命令，但 Actions 不部署页面。建议提供：

```bash
npx wrangler pages deployment list --project-name preferred-sub-generator
```

或部署后检查清单。

---

## P3-8. Webhook 通知失败会让整个更新失败

**位置**：`file scripts/update-kv.js`

`notifyWebhook(payload)` 没有 try/catch。如果 webhook 失败，KV 已写入但脚本失败。

**建议**：通知失败只 warning，不影响主流程。

# P4 · API / 客户端体验

## P4-1. `/sub` 缺少 HEAD/ETag 条件请求支持

当前生成 ETag，但没有处理 `If-None-Match`。客户端频繁拉取订阅时，仍返回完整内容。

**建议**：在 `cachedTextResponse` 或 API 层处理 304。

---

## P4-2. `/sub?type=singbox` Content-Type 是 text/plain

`generateSingboxSubscription` 返回 JSON 字符串，建议 content-type：

```text
application/json; charset=utf-8
```

---

## P4-3. `/sub?type=v2rayng` base64 不带换行，通常可用但可加兼容选项

建议支持：

```text
/sub?type=v2rayng&wrap=76
```

部分老客户端/复制场景更友好。

---

## P4-4. 模板槽位参数命名不完全一致

`/sub` 用 `template=1`，`/api/template` 用 `slot=1`。

建议统一，同时保留兼容：

```text
slot=1
```

`template=1` 作为 alias。

---

## P4-5. `/best?version=last` 只支持 last 或精确 key，缺少版本列表

建议新增：

```text
GET /versions
```

返回最近 N 个 `BEST_IPS_*` key，方便回滚和诊断。

---

## P4-6. 错误响应不带机器可读 code

例如：

```json
{ "error": "No available nodes" }
```

建议：

```json
{ "ok": false, "code": "NO_AVAILABLE_NODES", "message": "..." }
```

---

## P4-7. `/status` 没有 stale 判定

建议 STATUS 带 `updatedAt` 年龄判断：超过 12 小时 stale，超过 24 小时 unhealthy。

---

## P4-8. 首页保存模板后展示完整 preview.uuid

**位置**：`file src/api/template.js` POST 返回 `preview = toTemplatePreview(template)`，包含完整 uuid。

虽然这是管理操作后的响应，但页面如果被旁观/截图会暴露 UUID。

建议 POST 也返回 `templateSafe`，完整解析只内部使用。

---

## P4-9. 订阅接口没有 `download` 文件名提示

可加：

```text
Content-Disposition: inline; filename="preferred-sub.yaml"
```

方便客户端下载和识别。

## 6. 结论

`preferred-sub-generator` 的代码质量和测试基础比一般小项目好很多，真正的问题不是“能不能跑”，而是**私有订阅项目的隐私边界还不够硬**。

如果只是自己临时用、域名不外传，当前项目可用；但如果要长期稳定使用，我建议先完成 P0 的 4 件事：

```text
/sub 只读 token
/sub private/no-store
禁用 query token
页面不再接受 ?token=
```

这几项做完后，项目才更符合它 README 里“单用户私用、不把真实节点交给第三方”的目标。
